## 2. Почему node_modules находится в корне и НЕ ДОЛЖЕН быть внутри public?

Вопрос границ изоляции клиентского и серверного кода часто задается на защите дипломных и курсовых проектов.

### Как работает каталог `public/`
В `server.js` статический слой подключается одной строкой:
```javascript
app.use(express.static(path.join(__dirname, 'public')));
```
Это означает, что веб-сервер Express отдает **любой файл** из папки `public` любому пользователю интернета без авторизации. Если в строке браузера ввести `http://localhost:3030/css/style.css`, сервер просто прочитает файл с диска и отдаст его клиенту как текст.

### Что такое `node_modules/`
Папка `node_modules` содержит тысячи пакетов и библиотек, необходимых **только серверной платформе Node.js** (`express`, `better-sqlite3`, `bcryptjs`, `jsonwebtoken`, `nodemailer` и др.).

### Почему `node_modules` обязан быть изолирован в корне:

1. **Безопасность (Security Boundaries):**
   Если поместить `node_modules` внутрь `public/`, любой посетитель сайта сможет скачать исходные коды библиотек, тестовые файлы пакетов, скрытые скрипты сборки и файлы лицензий. Злоумышленник сможет мгновенно определить точные минорные версии всех зависимостей и применить известные уязвимости (CVE).

2. **Несовместимость сред исполнения:**
   Серверные библиотеки написаны под среду Node.js. Например, `better-sqlite3` содержит скомпилированные бинарные C++ аддоны (`.node`), которые взаимодействуют напрямую с операционной системой Windows или Linux. Браузер клиента физически не может выполнить бинарный файл драйвера базы данных.

3. **Сетевой трафик и объем:**
   Каталог `node_modules` занимает от 50 до 300+ мегабайт и содержит десятки тысяч файлов. Публикация его в веб открывает возможность индексирования поисковыми роботами сотен тысяч бессмысленных файлов, перегружая сервер и расходуя трафик.

4. **Утечка секретов:**
   Некоторые серверные пакеты в каталогах тестов могут содержать примеры приватных ключей или дефолтных паролей. Размещение их в публичной директории создает критическую дыру в безопасности.

> **Вывод:** Клиентский код (`public/`) и серверный код (`src/`, `node_modules/`, `data/`) строго разделены. Браузер общается с сервером исключительно через контролируемый REST API (`/api/*`), никогда не имея прямого доступа к файловой системе сервера.

## 3. Сквозной жизненный цикл запроса (Request Lifecycle)

Рассмотрим, как взаимодействуют файлы проекта на примере реального действия: покупатель оформляет заказ с промокодом в корзине.

```
[Браузер Покупателя]
       │
       ▼  (1) Нажатие «Оформить заказ и оплатить»
[public/js/cart.js] ──► Проверяет токен в localStorage ('user_token')
       │                Если токена нет ──► Открывает модалку регистрации (Push-код)
       │                Если токен есть  ──► Формирует JSON с товарами и кодом 'MODUL2026'
       │
       ▼  (2) HTTP POST /api/orders (с заголовком Authorization: Bearer <JWT>)
[server.js] ──► Направляет запрос в роутер заказов
       │
       ▼
[src/middleware/auth.js] (optionalAuth) ──► Проверяет валидность JWT токена
       │                                     Извлекает user_id = 105
       │
       ▼
[src/routes/orders.js]
       ├─► (3) Проверяет промокод в справочнике PROMOCODES ('MODUL2026' = 5%)
       ├─► (4) Считает итоговую сумму: 1 000 000 ₽ - 50 000 ₽ = 950 000 ₽
       ├─► (5) Вызывает [src/db/database.js]:
       │       INSERT INTO orders (...) VALUES (...) в [data/store.db] (режим WAL)
       │
       ├─► (6) Асинхронно вызывает сервисы оповещений:
       │       ├─► [src/services/mailer.js]: Dual Relay письмо на watislove@internet.ru
       │       │   (пишет лог в [data/outbox.log])
       │       └─► [src/services/telegram.js]: Запрос в Telegram Bot API
       │
       ▼  (7) Ответ сервера: { orderId: 128, paymentUrl: '/payment.html?orderId=128' }
[public/js/cart.js] ──► Очищает корзину в localStorage
       │
       ▼  (8) Перенаправление на оплату
[public/pages/payment.html] ──► Симуляция 3D-Secure ──► POST /api/orders/webhook/yookassa
       │
       ▼  (9) Переход на финал
[public/pages/profile.html] ──► Показывает заказ в статусе «Оплачен» и кнопку договора
```

## 4. База данных и механизм SQLite WAL

Проект использует встраиваемую реляционную СУБД SQLite через высокопроизводительный драйвер `better-sqlite3`.

В файле `src/db/database.js` первой строкой выполняется:
```javascript
db.pragma('journal_mode = WAL');
```
**WAL (Write-Ahead Logging)** — это механизм, при котором:
- Все изменения (новые заказы, смена статусов) сначала последовательно дописываются во временный файл `data/store.db-wal`.
- Читатели (пользователи сайта, просматривающие каталог) читают основную базу `data/store.db`, не блокируя пишущий процесс, и не ждут завершения транзакции.
- Благодаря WAL интернет-магазин выдерживает высокую конкурентную нагрузку без ошибок вида `database is locked`.

## 5. Изоляция конфигурации и секретов (.env)

- **`.env`** содержит секретные ключи, реальные пароли внешних сервисов (SMTP, Telegram, ЮKassa) и добавлен в `.gitignore`. Он никогда не попадает в публичные коммиты Git.
- **`.env.example`** содержит безопасный шаблон с описанием всех ключей, чтобы любой другой разработчик мог склонировать репозиторий, выполнить `cp .env.example .env` и запустить проект за 1 минуту.
- В кодовой базе реализована защита от сбоев: если секретный ключ Telegram или боевой пароль почты не задан в `.env`, система **не падает**, а мягко переключается на безопасные фолбеки (FormSubmit Relay, симуляция push-кодов в консоль, Sandbox-шлюз).
